NutriCare — Security Sheet

Application version: 1.1.0
Document date: July 2026
Classification: Commercial Use

1. Application Overview

NutriCare is a Windows desktop application for professional nutritional patient management. It runs entirely on the user's local PC: no proprietary cloud server is required and no health data is transmitted externally.

  • Stack: Spring Boot 3.3.5 + JavaFX 21 (bundled JVM runtime)
  • Database: H2 embedded (local file, not network-exposed)
  • Installer: MSI for Windows, built with jpackage + WiX Toolset 3.x
  • User data path: %USERPROFILE%\.nutricare\

3. Security Measures Implemented

Measure Implementation Detail
Localhost-only network binding server.address=127.0.0.1 in application.properties. Tomcat does not respond to requests from the local network (LAN, VPN, etc.).
H2 console disabled spring.h2.console.enabled=false. The H2 web administration interface is never started in production builds.
API key encryption (AES-256-GCM) AI provider API keys are never written in plaintext. Before persistence they are encrypted with AES-256-GCM. The encryption key is bundled in the JAR (appropriate for a single-tenant desktop app).
RSA-2048 offline license system The license is a digitally signed file (SHA-256withRSA) tied to the machine ID (SHA-256 hash of MAC address + hostname). The private key is not distributed with the application; verification uses only the embedded public key.
Development configuration isolation application-dev.properties is excluded from the production JAR via a Maven resource filter. No development settings (e.g., H2 console enabled) reach the distributed package.
Per-OS-user data isolation The database resides in %USERPROFILE%\.nutricare\: each Windows user accesses only their own data, enforced transparently by NTFS permissions.
Bundled JVM (isolated runtime) The Java runtime is included in the installer (jpackage). It does not depend on the system JVM and does not share a classpath with other applications.

4. Residual Risks & Recommendations

Risk Scenario Recommended Mitigation
Physical machine access An attacker with physical access to the machine can read the H2 file directly from the filesystem Enable BitLocker (or EFS) on the volume containing %USERPROFILE%. This is an OS-level policy requirement, not an application concern.
AI prompt with sensitive data The user includes patient PII in the prompt sent to the AI model Train users to use pseudonyms or anonymous identifiers in the diet generator. The feature generates dietary text — it does not require patient identifiable data.
Data backup The H2 file is not backed up automatically; a disk failure causes data loss Include %USERPROFILE%\.nutricare\ in the corporate backup policy (Windows Backup, robocopy, Veeam, etc.).

5. GDPR Compliance — Application-Level Elements

  • Data residency: health data remains on the local PC; no transfer to proprietary cloud servers.
  • Data minimization: the application collects only data explicitly entered by the nutritionist (patient records, measurements, visit notes).
  • Right to erasure: the nutritionist can delete individual patients from the UI; a full uninstall removes all data by deleting %USERPROFILE%\.nutricare\.
  • DPA: a Data Processing Agreement specific to NutriCare is available upon request.
